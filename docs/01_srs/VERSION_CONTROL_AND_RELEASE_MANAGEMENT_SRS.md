## ১. মডিউল পরিচিতি ও ব্যবসায়িক উদ্দেশ্য (Introduction & Objectives)

### ১.১ প্রেক্ষাপট
একটি আন্তর্জাতিক ডেনিম কারখানায় যেখানে ২০টি Jeanologia লেজার মেশিন সার্বক্ষণিক চলছে, সেখানে সফটওয়্যার আপডেট বা বাগ ফিক্সের জন্য প্রোডাকশন বন্ধ রাখা চরম আর্থিক ক্ষতি ডেকে আনে। 
এছাড়াও কোনো আপগ্রেডে যদি ডেটাবেজের আগের ডাটা ক্ষতিগ্রস্ত হয় বা ২০টি মেশিনে আলাদা আলাদা করে পেনড্রাইভ দিয়ে আপডেট করতে হয়, তবে তা মারাত্মক বিশৃঙ্খলা তৈরি করে। 
তাই **ভার্সন কন্ট্রোল ও রিলিজ ম্যানেজমেন্ট এসআরএস** নিশ্চিত করে যে—ডেভেলপারের যেকোনো আপডেট সেন্ট্রাল সার্ভারে সাব-১০ সেকেন্ডে জিরো-ডাউনটাইমে কার্যকর হবে, ডেটাবেজ কোনো ডাটা লস ছাড়া মাইগ্রেট হবে এবং ২০টি মেশিনের এজ-এজেন্ট কোনো তার বা পেনড্রাইভ ছাড়াই লোকাল ল্যানের মাধ্যমে স্বয়ংক্রিয়ভাবে আপডেট হবে।

### ১.২ মূল উদ্দেশ্য
1. **জিরো-ডাউনটাইম কনটেইনার আপডেট**: সেন্ট্রাল ডাটাবেজ বন্ধ না করেই ব্যাকগ্রাউন্ডে ৫-১০ সেকেন্ডের মধ্যে ব্যাকএন্ড ও ফ্রন্টএন্ড আপডেট লাইভ করা।
2. **১০০% সেফ ডেটাবেজ মাইগ্রেশন (Alembic)**: আগের সমস্ত অর্ডার, কিউআর ও প্রোডাকশন হিস্ট্রি অক্ষুণ্ণ রেখে নতুন টেবিল ও কলাম যুক্ত করা।
3. **এজ-এজেন্ট সেন্ট্রাল অটো-আপডেট (Zero Physical Intervention)**: মেশিনের কাছে না গিয়ে সেন্ট্রাল সার্ভার থেকে লোকাল ল্যানে ২০টি মেশিনের `laser_agent.exe` আপডেট পুশ করা।
4. **১-ক্লিক ইমার্জেন্সি রোলব্যাক**: নতুন আপডেটে কোনো ত্রুটি দেখা দিলে ১ মিনিটে পূর্বের স্থিতিশীল ভার্সনে ফিরে যাওয়ার সক্ষমতা।

## ২. গিট ব্রাঞ্চিং স্ট্র্যাটেজি ও সেমেন্টিক ভার্সনিং (Git Workflow & SemVer)

### ২.১ সেমেন্টিক ভার্সনিং স্ট্যান্ডার্ড (`vMAJOR.MINOR.PATCH`)
* **MAJOR (v2.0.0)**: আর্কিটেকচারাল পরিবর্তন বা ব্রেকিং এপিআই পরিবর্তন।
* **MINOR (v1.1.0)**: নতুন ফিচার বা নতুন স্ক্রিন সংযোজন (Backward Compatible)।
* **PATCH (v1.0.1)**: কোনো ছোটখাটো বাগ ফিক্স বা পারফরম্যান্স টিউনিং।

### ২.২ গিট ব্রাঞ্চ পলিসি (Branching Strategy)
* `main`: প্রোডাকশন ব্রাঞ্চ। সিটিও স্যারের চূড়ান্ত সাইন-অফ ও ট্যাগ ব্যতীত এখানে সরাসরি কোনো কোড পুশ সম্পূর্ণ নিষিদ্ধ।
* `develop`: অ্যাক্টিভ ডেভেলপমেন্ট ও ইন্টিগ্রেশন ব্রাঞ্চ।
* `hotfix/*`: লাইভ কারখানায় জরুরি কোনো ফিক্স দেওয়ার জন্য তাৎক্ষণিক আইসোলেটেড ব্রাঞ্চ।

## ৩. ডেটাবেজ স্কিমা ভার্সন কন্ট্রোল (Alembic Migration Specification)

### FR-VER-01: ম্যানুয়াল এসকিউএল রান নিষিদ্ধকরণ (Zero Manual DDL)
- প্রোডাকশন ডেটাবেজে সরাসরি কোনো `ALTER TABLE` বা `CREATE TABLE` কমান্ড চালানো সম্পূর্ণ নিষিদ্ধ।
- প্রতিটি ডাটাবেজ পরিবর্তন Alembic মাইগ্রেশন স্ক্রিপ্টে ভার্সন করা থাকবে (যেমন: `migrations/versions/001_initial_schema.py`)।

### FR-VER-02: প্রি-মাইগ্রেশন অটো-স্ন্যাপশট (Pre-Migration Safety Snapshot)
- ডেটাবেজে কোনো মাইগ্রেশন স্ক্রিপ্ট রান করার ঠিক পূর্বে ব্যাকগ্রাউন্ডে একটি অটোমেটিক পয়েন্ট-ইন-টাইম স্ন্যাপশট তৈরি হবে:
  `docker compose exec lacs-db pg_dump -U lacs_admin lacs_production > pre_migration_backup.sql`
- মাইগ্রেশন ফেইল করলে সিস্টেম স্বয়ংক্রিয়ভাবে পূর্বের স্ন্যাপশট রিস্টোর করবে।

### FR-VER-03: রিভার্সিবল আপগ্রেড ও ডাউনগ্রেড পলিসি
- প্রতিটি মাইগ্রেশন ফাইলে বাধ্যতামূলকভাবে `upgrade()` এবং `downgrade()` দুটি মেথডই থাকতে হবে, যাতে যেকোনো পরিবর্তন সহজে প্রত্যাহার করা যায়।

## ৪. সেন্ট্রাল সার্ভার ডকার রোলিং আপডেট স্পেক (Zero-Downtime Deployment)

### FR-VER-04: আইসোলেটেড ব্যাকএন্ড রি-বিল্ড
- সেন্ট্রাল সার্ভারে আপডেট কার্যকর করার সময় ডেটাবেজ কনটেইনার (`lacs-db`) স্পর্শ করা হবে না; ডাটাবেজ সার্বক্ষণিক রানিং থাকবে।
- শুধুমাত্র ব্যাকএন্ড সার্ভিস রিবিল্ড হবে:
  ```bash
  docker compose up -d --build --no-deps lacs-backend
  ```
- সময়: সর্বোচ্চ **৫ থেকে ১০ সেকেন্ড**। কারখানার কোনো মেশিন ড্রপ হবে না।

### FR-VER-05: ইনস্ট্যান্ট ১-ক্লিক রোলব্যাক স্ক্রিপ্ট (`rollback.sh`)
- কোনো কারণে নতুন রিলিজ ফেইল করলে অপারেটর বা ইঞ্জিনিয়ার ১টি স্ক্রিপ্ট রান করবেন:
  ```bash
  ./scripts/rollback.sh v1.0.0
  ```
- স্ক্রিপ্টটি সাথে সাথে পূর্ববর্তী স্টেবল গিটের ট্যাগ চেকআউট করে কনটেইনার রি-ডিপ্লয় করবে।

## ৫. ২০টি Jeanologia মেশিনে এজ-এজেন্টের লোকাল ল্যান অটো-আপডেট (Edge OTA via LAN)

কোনো পেনড্রাইভ বা ম্যানুয়াল ইন্টারভেনশন ছাড়া ২০টি মেশিনের উইন্ডোজ আইপিসিতে এজেন্ট কীভাবে আপডেট হবে:

```
[ সেন্ট্রাল সার্ভার ] (নতুন ভার্সন রিলিজ: laser_agent_v1.0.1.exe)
        │
        ├──▶ WebSocket ব্রডকাস্ট সিগন্যাল: { event: "AGENT_UPDATE_AVAILABLE", version: "v1.0.1" }
        │
[ ২০টি Jeanologia এজ-এজেন্ট (লিসেনিং) ]
        │
        ├──▶ ধাপ ১: আইডল চেক (মেশিনে বর্তমানে কোনো লেজার ফায়ার চলছে কি?)
        │            ├── YES: অপেক্ষা করো (লেজার শেষ হওয়া পর্যন্ত)
        │            └── NO: লোকাল ল্যান থেকে ডাউনলোড শুরু (Sub-1s via Cat6)
        │
        ├──▶ ধাপ ২: SHA-256 হ্যাশ ভেরিফিকেশন (ফাইলটি ১০০% অবিকৃত কি না)
        │
        ├──▶ ধাপ ৩: ব্যাকআপ তৈরি (current laser_agent.exe ➔ laser_agent.bak)
        │
        ├──▶ ধাপ ৪: অ্যাটমিক রিপ্লেস ও সার্ভিস রিস্টার্ট (NSSM Windows Service)
        │
        └──▶ ধাপ ৫: সার্ভারে কনফার্মেশন পাঠানো: { machine_id: "M07", status: "UPDATED_TO_v1.0.1" }
```

### FR-VER-06: আইডল-স্টেট ডিটেকশন (Idle-State Safety Gate)
- অপারেটর যখন প্যান্টে লেজার ফায়ার করছেন, সেই মুহূর্তে এজেন্ট কখনোই আপডেট নেবে না।
- কনভেয়ার ও eMark যখন সম্পূর্ণ শান্ত (Idle) থাকবে, শুধুমাত্র তখনই ব্যাকগ্রাউন্ডে ৩ সেকেন্ডের মধ্যে সার্ভিস রিস্টার্ট হবে।

### FR-VER-07: ফল্ট-ব্যাক মেকানিজম (Auto-Rollback on Agent Crash)
- নতুন এক্সিকিউটেবল ফাইলটি চালু হওয়ার পর যদি প্রথম ৫ সেকেন্ডের মধ্যে সেন্ট্রাল সার্ভারে হার্টবিট পাঠাতে ব্যর্থ হয়, তবে স্ক্রিপ্টটি স্বয়ংক্রিয়ভাবে নতুন ফাইলটি ডিলিট করে পূর্বের `laser_agent.bak` ফাইল চালু করে ফেলবে।

## ৬. ডেটাবেজ ট্র্যাকিং টেবিল (Release Management Tables)

### টেবিল ১: `system_releases` (সিস্টেম রিলিজ অডিট)
```sql
CREATE TABLE system_releases (
    id UUID PRIMARY KEY, -- RFC 9562 UUIDv7
    version_tag VARCHAR(30) UNIQUE NOT NULL, -- e.g. 'v1.0.1'
    release_type VARCHAR(20) NOT NULL,       -- MAJOR, MINOR, HOTFIX
    release_notes TEXT,
    deployed_by UUID NOT NULL REFERENCES users(id),
    deployed_at TIMESTAMPTZ DEFAULT NOW(),
    rollback_at TIMESTAMPTZ,
    status VARCHAR(20) DEFAULT 'ACTIVE'      -- ACTIVE, ROLLED_BACK
);
```

### টেবিল ২: `machine_agent_versions` (২০টি মেশিনের লাইভ ভার্সন ট্র্যাকার)
```sql
CREATE TABLE machine_agent_versions (
    machine_id UUID PRIMARY KEY REFERENCES laser_machines(id),
    current_version VARCHAR(30) NOT NULL,
    last_updated_at TIMESTAMPTZ DEFAULT NOW(),
    update_status VARCHAR(30) DEFAULT 'UP_TO_DATE', -- UP_TO_DATE, DOWNLOADING, FAILED, RETRYING
    last_error TEXT
);
```

## ৭. অকার্যকরী রিকোয়ারমেন্টস (Non-Functional Requirements - NFR)

* **NFR-VER-01**: সেন্ট্রাল সার্ভারের কনটেইনার আপগ্রেড ডাউনটাইম অনূর্ধ্ব **১০ সেকেন্ড**।
